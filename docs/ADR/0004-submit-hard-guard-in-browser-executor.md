# ADR-0004：在浏览器执行层实施全路径 Submit Hard-Guard

- **状态**：已采纳（M0 基线）
- **日期**：2026-11-24

## 背景
网申最终提交属于不可逆外部副作用。如果仅在名为 `submit` 的工具上加确认弹窗，模型仍可能通过普通 `act(click)` 点击提交按钮、在表单内按 `Enter` 键、使用坐标点击或通过 `run` 执行页面 JavaScript（如 `form.submit()`）意外触发提交。

## 决策
1. **首版默认采用“人工最终提交”模式**：助手完成全部可填字段、回读核对并调用 `report_filling_ready` 后，展示包含岗位、关键字段、缺失项、附件清单与截图的核对卡，引导用户在右侧真实网页亲自点击提交；随后助手（或用户触发）执行只读回执核验。
2. **全路径执行层硬闸门**：在 `@jobhelper/browser-bridge` 统一拦截所有写动作：
   - 元素点击：检查标签文本、`aria-label`、按钮 `type="submit"` 及所属表单语义；
   - 键盘按键：默认禁止在表单内发送 `Enter`；
   - 坐标点击：点击前强制 `elementFromPoint` 反查实际 DOM 元素并复用同一提交语义规则，跨 iframe 命中直接转人工；
   - `run` 工具：v1 取消自由 JS 执行权限，收敛为受控的只读声明式探针；
   - 语义模糊按钮：无法确认是否为最终提交时，宁可暂停交给用户核对，绝不盲点。
3. **预留可审计授权模式契约**：`ConfirmationService` 仍完整设计 `taskId + confirmationId + operation + contentHash` 单次消费机制，以便未来按需支持“批准后由助手点击一次”而不必重构状态模型。

## 权衡与后果
- **收益**：从根本上兑现“未经用户确认绝不自动提交”的产品安全承诺，把不可逆误投风险降至最低。
- **代价**：部分包含多步向导（“下一步”误判风险）的招聘站需要通过站点 Skill 和 `inspect_control` 精准标注非提交导航按钮，避免过度拦截影响体验。
