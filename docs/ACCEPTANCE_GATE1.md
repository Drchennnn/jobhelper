# Gate 1 黄金闭环与安全边界验收方案

> 本方案对应 [主代理交接-锦鲤架构与本地投递助手.md](../主代理交接-锦鲤架构与本地投递助手.md) 第 7 节定义的**首个验收目标**。在 Gate 1 全部通过之前，不得宣称投递闭环可用，也不盲目展开数十个外部招聘站点的专项适配。

---

## 1. 验收前置条件与测试夹具

- **虚构测试档案**：一份完整虚构个人简历 JSON（故意留空 1 个非标准字段，如“是否接受出差”或“毕业设计题目”，用于触发问题卡）+ 1 份测试 PDF 简历附件。
- **BYOK 模型配置**：至少 1 组用户自备可用模型 API 配置（完成连通性及 `tool_calling` 探测）。
- **可重置本地测试表单（`fixtures/mock-ats`）**：
  - `GET /reset`：一键清空服务端状态与表单记录。
  - `GET /login`：模拟招聘站点登录页（含密码框、模拟验证码框，验证 Agent 拒绝自动填写并请求人工接管）。
  - `GET /apply/job-001`：模拟网申表单（包含姓名、手机、邮箱、学历下拉、期望城市、多行项目经历、自定义必填题、PDF 简历上传、`保存草稿`按钮、`最终提交`按钮）。
  - `POST /api/submit`：支持通过查询参数或切换开关注入三种回执模式：
    - `mode=success`：正常返回包含岗位名与申请编号的“投递成功”回执页；
    - `mode=timeout`：服务端已落库但延迟/断连不返回回执页（模拟提交结果不明）；
    - `mode=error`：返回 500 校验错误。

## 2. 黄金主路径（8 步端到端验收）

| 步骤 | 操作 | 必须观测到的系统行为与落库证据 |
|---|---|---|
| **G1-01** | 在桌面工作台配置 BYOK 模型并测试连接，导入虚构档案与测试 PDF | 设置页显示 `tool_calling` / `streaming` / `vision` 真实探测结果；SQLite `model_providers` 中不含明文 API Key |
| **G1-02** | 通过总助手或粘贴 URL 创建 `job-001` 投递任务 | 创建前显示岗位、URL、所选档案版本及附件确认；`tasks` 表写入新任务并锁定 `profile_version_id`；右栏加载真实网页 |
| **G1-03** | 启动任务，进入模拟登录页 | 助手只读观察，不触碰密码/验证码框，调用 `request_user_action(login)`；四轴状态为 `waiting_user / login / opened / not_submitted` |
| **G1-04** | 用户在右侧网页手动完成登录，点击「已处理，请检查」 | 签发新 `runId` 与新 `epoch`；助手先重新 `observe` 确认已进入申请表，开始逐项填写文本、下拉与上传测试 PDF，每项回读核对一致 |
| **G1-05** | 遇到档案中缺失的必填问题，弹出结构化问题卡 | 助手不捏造答案；用户回答后答案按 `callId + questionId` 回传并正确填入表单 |
| **G1-06** | 填表过程中用户点击「我来操作」，在右侧网页手动修改某一字段值，再点「已处理，请检查」 | 点击接管时先进入 `stopping`、撤销租约与 CDP，切为 `paused(manual_control)`；恢复后生成新 `epoch` 并重新 `observe`，**准确读到用户修改后的新值**，不把用户改过的值覆盖回旧值 |
| **G1-07** | 所有字段填完并回读无误，进入核对阶段 | 调用 `report_filling_ready` 与 `request_submission_confirmation`；状态为 `waiting_user / submission_confirmation / filling_ready / not_submitted`（**绝不能显示已投递**）；左栏展示完整核对卡（字段摘要、附件、截图） |
| **G1-08** | 用户在右侧真实网页亲自点击最终提交（`mode=success`），随后触发结果检查 | 记录提交发生与官网回执证据；四轴状态收敛为 `closed / none / done / submitted_verified`；求职进度表同步更新且标注来源为官网回执 |

## 3. 安全与异常边界验收（10 项必测项）

| 编号 | 故障/攻击注入场景 | 必须满足的通过标准 |
|---|---|---|
| **G1-S01** | **迟到旧 epoch 动作注入**：在用户接管（`stopTask`）后，直接向 `ScopedCdpBridge` / `BrowserController` 发送携带旧 `epoch` 的点击/输入指令 | 指令 100% 被拒绝并返回租约失效错误，网页 DOM 无任何变更 |
| **G1-S02** | **Submit Hard-Guard 全路径阻断**：诱导或测试调用 `act(click, 提交按钮)`、`act(press, 'Enter')`、坐标点击提交按钮、以及尝试执行脚本提交 | 全部 4 条路径均在执行层被硬拒绝；测试服务端收到的提交请求数为 `0` |
| **G1-S03** | **核对卡防篡改失效**：核对卡展示后，用户接管修改任意字段或更换附件 | 原 `confirmationId` 自动置为 `invalidated`，必须重新生成新 `contentHash` 的核对卡 |
| **G1-S04** | **模拟回执超时（`mode=timeout`）**：点击提交后接口断连无回执，随后执行恢复/重试操作 | 任务停在 `waiting_user / result_check / verifying / unknown`；提供“重新检查页面”入口，**绝不自动再次点击提交** |
| **G1-S05** | **应用进程强制退出与重启**：任务处于 `running` 状态时强杀 Electron 主进程并重启 | 任务恢复为 `interrupted`，`epoch` 为空，历史事件与 `action_ledger` 完整保留，提示用户核对网页后手动继续，不自动重放写操作 |
| **G1-S06** | **问题卡超时与迟到回答**：让 `ask_user_question` 超过等待窗口（测试可将超时调短为 5 秒），随后再提交答案 | 超时后问题卡维持 `pending`（不跳过/不猜测）；用户稍后提交的答案绑定原 `questionId` 进入下一轮，不重复发问 |
| **G1-S07** | **切换全局默认档案**：`job-001` 运行或暂停期间，在档案中心新建档案 B 并设为全局默认 | `job-001` 的 `profile_version_id` 与工具读取结果仍为旧档案快照 A；新创建的 `job-002` 使用档案 B |
| **G1-S08** | **重复开始同一岗位**：在 `job-001` 未结束时再次从总助手或 URL 入口提交 `job-001` | 复用并跳转打开原 `taskId`，数据库中不产生第二条未完成任务 |
| **G1-S09** | **多岗位并行隔离**：总助手一次派发 `job-001`（档案 A）与 `job-002`（档案 B） | 两个任务各自独立标签页、独立上下文与独立档案，CDP 无法跨任务读取对方页面；总助手会话保持完整 |
| **G1-S10** | **BYOK API 超时/429 限流**：测试端点返回超时或 429 错误 | 任务转入 `error`，UI 显示真实服务商错误与已完成步骤，允许切换模型配置后从当前页面继续，不从头重填 |
